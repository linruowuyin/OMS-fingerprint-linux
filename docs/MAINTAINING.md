# Maintaining this project

Release checklist for the two distribution channels and the upstream
submission. Everything here is scripted or copy-pasteable.

## Repository map

| Path | Purpose | Published to |
|---|---|---|
| `driver/` | Driver source, tests, upstream patch | GitHub (this repo) |
| `driver/upstream/` | MR-ready patch + issue text | → libfprint (GitLab) |
| `aur/libfprint-omsmoc/` | Generic Arch package | → AUR |
| `aur/libfprint-omsmoc-wujie14pro/` | Machine-specific variant | → AUR |
| `aur/libfprint-omsmoc-wujie14pro/source-repo/` | Patch hosting repo | → GitHub |

The patch hosting repo exists because **AUR only accepts source packages** —
it cannot carry local files in the package repository. The driver patch must
therefore live at a `raw.githubusercontent.com` URL, tagged per libfprint
version.

| Component | Where |
|---|---|
| Driver repository | <https://github.com/linruowuyin/OMS-fingerprint-linux> |
| Patch hosting | <https://github.com/linruowuyin/omsmoc-patches> |
| Upstream | <https://gitlab.freedesktop.org/libfprint/libfprint> |

## 1. Releasing a new libfprint version

### 1.1 Regenerate the patch

The patch is built from the driver repository's own history. To produce it,
apply the driver changes to a clean libfprint tree and export the commit:

```bash
git clone https://gitlab.freedesktop.org/libfprint/libfprint
cd libfprint
git checkout v1.94.100

# apply the driver changes from the driver repository
git am --3way /path/to/OMS-fingerprint-linux/driver/upstream/0001-drivers-Add-support-for-OMS-match-on-chip-sensors.patch

# re-export as a single patch
git format-patch -1 --stdout > omsmoc-driver.patch
sha256sum omsmoc-driver.patch
```

Copy the result to **all** of these — they must stay byte-identical:

```
aur/libfprint-omsmoc/omsmoc-driver.patch
aur/libfprint-omsmoc-wujie14pro/omsmoc-driver.patch
aur/libfprint-omsmoc-wujie14pro/source-repo/omsmoc-driver.patch
```

Verify they match:

```bash
sha256sum aur/libfprint-omsmoc/omsmoc-driver.patch \
          aur/libfprint-omsmoc-wujie14pro/omsmoc-driver.patch \
          aur/libfprint-omsmoc-wujie14pro/source-repo/omsmoc-driver.patch
```

### 1.2 Push the patch and tag it

```bash
cd aur/libfprint-omsmoc-wujie14pro/source-repo
git add omsmoc-driver.patch
git commit -m "omsmoc-driver: libfprint 1.94.100 patch"
git tag -a v1.94.100 -m "libfprint 1.94.100 patch for OMS 33a7:2388"
git push origin main --tags
```

> **The raw CDN takes ~20 seconds to propagate a new tag.** A tag URL that
> returns 404 immediately after pushing is not necessarily broken — wait and
> retry. The `main` branch URL works immediately.

Verify before continuing:

```bash
curl -sL -o /tmp/p.patch -w "%{http_code}\n" \
  https://raw.githubusercontent.com/linruowuyin/omsmoc-patches/v1.94.100/omsmoc-driver.patch
sha256sum /tmp/p.patch     # must equal the hash from 1.1
```

### 1.3 Update the packages

In both `aur/libfprint-omsmoc/` and `aur/libfprint-omsmoc-wujie14pro/`:

* `pkgver` → the new libfprint version
* `pkgrel` → reset to `1`
* `sha256sums` → the new tarball hash and the new patch hash
* `_ghuser` → stays `linruowuyin`

Then regenerate `.SRCINFO` — it must never drift from `PKGBUILD`:

```bash
cd aur/libfprint-omsmoc
makepkg --printsrcinfo > .SRCINFO
```

### 1.4 Build and verify

```bash
rm -rf src pkg *.pkg.tar.zst
makepkg -f --noconfirm
```

Then check all five things:

```bash
# 1. tests passed
grep -c "^ok" src/libfprint-v1.94.100/build/meson-logs/testlog.txt   # expect 14

# 2. the driver is in the library
strings pkg/*/usr/lib/libfprint-2.so.2.0.0 | grep -E "FpiDeviceOmsMoc|libfprint-omsmoc"

# 3. the udev rule and the hwdb entry are present
ls pkg/*/usr/lib/udev/rules.d/
grep -o "v33A7p2388" pkg/*/usr/lib/udev/hwdb.d/*.hwdb

# 4. no local build path leaked into the binary
! strings pkg/*/usr/lib/libfprint-2.so.2.0.0 | grep -q "/home/"
```

> **On the build path.** libfprint's `fpi-device.c` includes
> `tests/fpi-test-emulation.h`, a file generated by `meson configure_file`
> that hardcodes the absolute build directory. That string ends up in the
> shipped library. `-ffile-prefix-map` does **not** help — it is a compile-time
> macro substitution and cannot touch a generated string constant. The
> packages therefore rewrite the generated header and recompile. Keep that
> block in `build()`.

### 1.5 Commit and push

```bash
cd /path/to/OMS-fingerprint-linux
git add -A
git commit
git push origin main
```

## 2. Publishing to the AUR

### 2.1 Prerequisites

* An AUR account with an SSH public key attached
  (<https://aur.archlinux.org/account/profile/>).
  AUR authorizes push **per key**: the key must be on the account, otherwise
  the server answers `Permission denied (publickey)` even though the key was
  offered correctly.
* The package name must be free:
  `curl -s -o /dev/null -w "%{http_code}" https://aur.archlinux.org/packages/<name>`
  → `404` means available.

### 2.2 Push

```bash
git clone ssh://aur@aur.archlinux.org/libfprint-omsmoc.git
cd libfprint-omsmoc

cp /path/to/OMS-fingerprint-linux/aur/libfprint-omsmoc/{PKGBUILD,.SRCINFO} .

git add PKGBUILD .SRCINFO
git commit -m "Initial import: libfprint with the OMS match-on-chip driver"
git push
```

Only `PKGBUILD` and `.SRCINFO` are pushed. The patch is referenced by URL, so
it must not be added.

### 2.3 After pushing

* Watch the build at <https://aur.archlinux.org/packages/libfprint-omsmoc>
* The build log is on the package page; a failure there is usually a bad
  checksum or a changed upstream tarball
* Bump `pkgrel` and re-push for any fix — never amend a published commit

## 3. Submitting upstream

Full instructions live in [`driver/upstream/README.md`](../driver/upstream/README.md).
The short version:

1. Get freedesktop GitLab permissions. New accounts cannot create projects or
   fork, and forking is a prerequisite for a merge request. File a
   **User verification** issue:
   <https://gitlab.freedesktop.org/freedesktop/freedesktop/issues/new?issuable_template=User%20verification>
2. If permissions are not granted yet, file a **Driver Request** issue instead —
   the text is ready to paste in
   [`driver/upstream/DRIVER-REQUEST.md`](../driver/upstream/DRIVER-REQUEST.md).
3. Once you can fork, open the merge request using the description in
   `driver/upstream/README.md`.

### Known upstream objection to pre-empt

Upstream's generated autosuspend hwdb sets `ID_AUTOSUSPEND=1` for every
supported device, but this chip cannot survive autosuspend. The packaging works
around it with a `power/control=on` udev rule. To land upstream, the driver
itself would have to implement reset/recovery, or the hwdb generator needs an
exception. State this proactively in the merge request description.

## 4. Compliance checklist

The CI pipeline enforces the mechanical parts of this. Keep it green.

```bash
# SPDX identifier and modification notice in every source file
for f in $(git ls-files 'driver/**/*.c' 'driver/**/*.h'); do
    grep -q 'SPDX-License-Identifier: LGPL-2.1-or-later' "$f" || echo "MISSING SPDX: $f"
    grep -q 'Modifications (2026-10-28)' "$f" || echo "MISSING NOTICE: $f"
done

# README attribution
grep -q '^## Attribution' README.md
grep -q 'BlueApple233/OMS-fingerprint-linux' README.md

# no build artifacts, no local paths
git ls-files | grep -E '\.pkg\.tar\.zst$|\.tar\.gz$|^build/'
git ls-files -z | xargs -0 grep -InE '/home/[a-z][a-z0-9_-]*/'
```

### Rules

* Every source file keeps the **original** copyright notice and adds a
  `Modifications (…)` block (LGPL §5(a) and §5(b)).
* Never commit vendor binaries, firmware or raw USB captures.
* The bundled capture must stay sanitized: no chip serial, no USB serial.
  `driver/tests/sanitize-capture.py` handles this and recomputes the frame
  checksums.
* The upstream URL of the original author stays in the copyright headers and
  the Attribution section. The repository URL in `url=` fields points here.
